# SO 的 PR 审批与合并规则

本文适用于 Sailing Out（简称 **SO**，`OE-Club/Sailing-Out`）。所有变更继续使用独立分支和面向 `main` 的 PR，通过 GitHub 的 PR 流程合并。

## 审批人及权限范围

- 新增 **cchhh（GitHub：[@ccchh4rr](https://github.com/ccchh4rr)，玩家移动负责人）** 为 SO 的 PR 审批人，保留现有其他审批人的权限和模块所有权。该昵称与 GitHub 账号的对应关系已由用户确认。
- cchhh 可在下列条件满足时审批他人的 SO PR；PR 作者不能审批自己的 PR。
- 审批资格不等于新增仓库管理员权限、合并权限或保护规则绕过权限。实际操作须符合该账号已有的 GitHub 权限；若需调整访问权限，必须单独核实准确账号及所需范围。

## 审批和合并的前提

以下条件必须同时满足，安全审查仅适用下一节的有限例外：

1. **Codex Review 代码审查通过。** 通过结论须对应当前 PR 最新的 head commit，审查发现的待修问题必须已处理。仅发出审查请求、审查进行中或旧提交的通过结论均不算通过；新增提交后须重新确认代码审查结论覆盖最新内容。
2. **CI 通过。** 当前 head commit 的所有适用 CI 均须成功，包括 `Repository checks (not Unity tests)`。失败、等待、取消、超时或状态未知都不能作为通过；不能通过跳过或禁用 CI 满足本条件。该仓库检查的范围见 [CI.md](CI.md)，其成功不代表 Unity 编译或 Edit/Play 测试已执行。
3. **没有合并冲突。** 合并前核对 PR 与最新 `main` 的可合并状态；如有冲突，先在任务分支解决并重新验证。可合并状态未知时，先完成核验。
4. **符合 GitHub 的全部保护要求。** 必需检查、审查要求及其他仓库保护继续适用；既有的其他审批要求不因增加 cchhh 而取消。

## 安全审查卡住时的例外

在 Codex Review 已通过、CI 已通过且没有合并冲突的前提下，如果**仅安全审查因服务、排队或执行问题卡住**，具备既有合并权限的人可以按仓库保护规则合并，无需把该安全审查当成已通过。

- 在 PR 中如实记录卡住的安全审查名称、链接、实际状态和原因，以及采用该例外的说明，保留后续跟进事项。
- 此例外不等于安全审查通过，也不自动豁免安全审查已经报告的漏洞或其他明确失败结果。
- 如果 GitHub 将该安全审查设为必需检查并阻止合并，仍须等待或处理阻塞。不得关闭检查、降低要求、使用管理员绕过或修改保护规则来合并。
- 此例外不适用于 Codex Review 未通过、CI 未通过或存在合并冲突。

## 助手执行边界

本文对项目成员的审批授权不构成给助手的永久审批许可。助手每次提交 GitHub `APPROVE` 审批前，仍必须获得用户针对当次 PR 和对应提交的明确确认；不得自批或绕过保护。代码审查报告本身也不等于已经提交 GitHub 审批。

## 文档规则与 GitHub 实际配置

这些是项目工作规则，不能据此宣称 GitHub 已自动强制执行全部条件。核验时应分别检查账号权限、分支保护和规则集；不能把文档授权等同于 GitHub 权限调整，也不能把不可读取的设置视为不存在。现有 `Require pull requests for main` 规则集及本地 Git 钩子继续保留。
